Question: Real-world values of SHQueryUserNotificationState on Windows 10/11 for: exclusive fullscreen game, borderless
fullscreen game, browser F11, YouTube video fullscreen in Chrome/Edge, PowerPoint slide show, Teams/Zoom screen sharing,
Windows 11 Do Not Disturb / Focus. Which return QUNS_BUSY vs QUNS_RUNNING_D3D_FULL_SCREEN vs QUNS_PRESENTATION_MODE?
Cite forum/issue reports (e.g. projects that pause on fullscreen).

## Findings

Method note: pages were read through a summarising fetch tool, not opened by hand. Code details below are as reported by it.

### What is documented (official docs)
- Enum values: NOT_PRESENT=1, BUSY=2, RUNNING_D3D_FULL_SCREEN=3, PRESENTATION_MODE=4, ACCEPTS_NOTIFICATIONS=5, QUIET_TIME=6, APP=7.
  Source: Microsoft Learn, [QUERY_USER_NOTIFICATION_STATE](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ne-shellapi-query_user_notification_state) (official docs).
- BUSY = "a full-screen application is running or Presentation Settings are applied". D3D_FULL_SCREEN = exclusive-mode Direct3D app.
  PRESENTATION_MODE = user turned on Windows presentation settings. Same page.
- During quiet time (first hour after first login / upgrade) the call returns the other blocking state if one applies, never QUIET_TIME. Same page.

### Real-world reports found
- electron-notification-state README (GitHub README, secondary): regular full-screen apps typically return BUSY, exclusive D3D returns RUNNING_D3D_FULL_SCREEN,
  a presentation can be BUSY or PRESENTATION_MODE. It also says Windows "quiet hours" are a different thing from QUIET_TIME and are checked by a separate function.
  https://github.com/felixrieseberg/electron-notification-state (the unpkg copy of the older fork README says the same about the enum).
- Chromium [ui/base/fullscreen_win.cc](https://chromium.googlesource.com/chromium/src/+/main/ui/base/fullscreen_win.cc) (source code): treats only
  RUNNING_D3D_FULL_SCREEN and PRESENTATION_MODE as fullscreen. BUSY is NOT used. It then falls back to a window-geometry check and a console check.
  Reason for ignoring BUSY is not stated there (UNVERIFIED guess: BUSY is too broad).
- PowerToys [src/common/utils/game_mode.h](https://github.com/microsoft/PowerToys/blob/main/src/common/utils/game_mode.h) (MIT, source code): `detect_game_mode()` returns true only for
  RUNNING_D3D_FULL_SCREEN. No rect checks.
- Flow Launcher `Win32Helper.IsForegroundWindowFullscreen()` does NOT call SHQueryUserNotificationState at all (see R13.2).

## Answer for Cuy
Official docs only define the values; no source found that measures borderless, F11, YouTube, Teams/Zoom or Focus.
Chromium and PowerToys both ignore BUSY and use D3D (+ presentation mode in Chromium), then rely on window geometry for the rest.
Keep the D3D + PRESENTATION_MODE check and the rect check; do not rely on BUSY or on Focus assist. Measure the unknown cases on a real PC (a 10-line probe logging the state).
