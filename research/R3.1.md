Question: Velopack with a .NET Framework 4.8 WinForms app: find GitHub issues/discussions (github.com/velopack/velopack)
or blog posts confirming it works, and known problems. Where exactly must VelopackApp.Build().Run() be called relative to
a single-instance Mutex and Application.Run? Any issue with apps that start hidden in the tray?

## Findings

**Package and framework support** (source: NuGet page)
- Velopack on NuGet: latest stable 1.2.161, updated 2026-09-29, MIT, repo github.com/velopack/velopack. Target frameworks listed: net472, netstandard2.0, net8.0/9.0/10.0. net48 is not listed directly, only "computed" (compatible through net472). https://www.nuget.org/packages/Velopack

**Where Run() goes** (source: official docs)
- `VelopackApp.Build().Run()` must be called exactly once, in the main binary (`--mainExe`), and should be "the first code" in `Main()`. https://docs.velopack.io/integrating/overview
- Reason given: Velopack launches your exe with hook arguments during install, update and uninstall, and the process exits from inside `Run()`. Any code above `Run()` would also run during those operations. (same page)
- At normal startup `Run()` also auto-applies a pending local update and restarts the app (on by default; off with `SetAutoApplyOnStartup(false)`). (same page)
- Getting started page: call it "at the start of your Main method". https://docs.velopack.io/getting-started/csharp

**Mutex / Application.Run** (UNVERIFIED, my inference from the facts above)
- The docs never mention a Mutex or Application.Run. Order that follows from the docs: `Run()` first, then the single-instance Mutex, then `Application.Run`. A Mutex taken before `Run()` would also be taken during hook invocations and before an auto-apply restart.

**Evidence that it works with .NET Framework / WinForms**
- A Windows Forms sample was added: PR #452, merged, opened 2025-01-10. https://github.com/velopack/velopack/pull/452
- Issue #253 (2024-10-03, closed, label bug): a net48 app packed with vpk 0.0.626; shortcuts were not created on some machines (reporter suspects VMs); workaround was creating them in code with `CreateShortcutForThisExe`. https://github.com/velopack/velopack/issues/253
- Issue #195 (2024-08-04, closed): WinForms user saw code after `Run()` not running after an update restart; resolved after the vpk tool version was matched to the NuGet version. https://github.com/velopack/velopack/issues/195
- PR #1101 (2026-10-14, merged): removes ValueTuple usage from the C# library to fix a crash on older .NET Framework apps where ValueTuple is missing. Which release contains it was not checked (UNVERIFIED). https://github.com/velopack/velopack/pull/1101

**Hidden in tray**
- No issue or doc about tray or hidden-start apps was found. What the docs do say: the FastCallback hooks (install/update/uninstall) must show no UI and must exit within 15 s (update) or 30 s (install/uninstall). https://docs.velopack.io/integrating/hooks
- Setup.exe launches the app right after install (one-click installer). https://docs.velopack.io/packaging/installer

## Answer for Cuy
Velopack 1.2.161 (MIT) lists net472 + netstandard2.0, so it should work with net48; there is a WinForms sample (PR #452) and no tray-specific issue was found.
Call `VelopackApp.Build().Run()` as the very first line of `Main()`, before any Mutex and before `Application.Run` (docs say "first code"; Mutex order is my inference, UNVERIFIED).
Pack with a vpk version equal to the NuGet version (issue #195) and keep hook code free of UI.
