Question: Can a .NET Framework 4.8 WinForms app use GlobalSystemMediaTransportControlsSessionManager (SMTC) to know that media
is playing? Which package is needed (Microsoft.Windows.SDK.Contracts? version), known threading/MTA problems, minimum Windows version,
and which apps report playback status to SMTC (Spotify, browsers, VLC). Is this simpler or more reliable than peak meters?

## Findings

**API and minimum Windows:** `Windows.Media.Control.GlobalSystemMediaTransportControlsSessionManager`, introduced in Windows 10 version 1809 (10.0.17763.0).
It has `RequestAsync()`, `GetCurrentSession()`, `GetSessions()` and events `CurrentSessionChanged` and `SessionsChanged`; it only covers apps that integrate with `SystemMediaTransportControls`
(Microsoft Learn, official: https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmanager - the signatures there are partly from the page's summary, the page itself has no code).
Per session, `GetPlaybackInfo().PlaybackStatus` is the playing/paused state (properties list: https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionplaybackinfo ; the enum values were not on the page I opened, so the exact names are UNVERIFIED).

**From .NET Framework 4.8:** yes. Microsoft documents installing the NuGet package `Microsoft.Windows.SDK.Contracts` in .NET Framework 4.x projects; the version chooses the minimum Windows:
10.0.17763.x = Windows 10 1809, 10.0.18362.x = 1903, 10.0.19041.x = 2004
(https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/desktop-to-uwp-enhance). Package page: latest 10.0.28000.2705 (updated 2026-08-26), netstandard2.0, compatible net461-net481,
dependencies System.Runtime.WindowsRuntime >= 4.6.0 and two others, about 3.61 MB, requires `PackageReference` format and NuGet 4+; its text says it covers APIs up to Windows 2004
(https://www.nuget.org/packages/Microsoft.Windows.SDK.Contracts). For Cuy: use the 10.0.17763.x line (1809) or newer; which exact version to pick is UNVERIFIED. Put this code in the net48 WinForms project, not in the netstandard2.0 core.

**Community wrapper:** https://github.com/jayfunc/WindowsMediaController (fork of DubyaDude's library) supports .NET Framework 4.6.1+ and .NET 5+, needs Windows 10 build 17763+,
wraps `GlobalSystemMediaTransportControlsSessionManager` with events and `GetPlaybackInfo()`. README notes: old csproj formats may not import it (add a `PackageReference`), and apps started by Task Scheduler need a window at startup.
README says nothing about threading.

**Threading / MTA:** Microsoft's own sample (C++/WinRT) initialises the multithreaded apartment in `main` and awaits `RequestAsync`
(Raymond Chen, Microsoft: https://devblogs.microsoft.com/oldnewthing/?p=108980; it also has a C# version, no minimum Windows stated). I found NO documented STA/MTA problem for this API from a WinForms app.
UNVERIFIED practice: call `RequestAsync().AsTask()` and `await` it instead of blocking `.Result`/`.Wait()` on the UI thread (a blocking call on an STA UI thread can deadlock; general async rule, not shown for this API).

**Which apps report:**
- Spotify desktop: yes. Win32 app updated to support the Windows media controls, play/pause from the volume flyout (news article, undated: https://onmsft.com/?p=85825).
- VLC: a merge request adds a `win_smtc` module (C++/WinRT) with play/pause/stop/next/previous, metadata and timeline, enabled by default (https://code.videolan.org/videolan/vlc/-/merge_requests/3010); the page does not give merge status or VLC version, so which release ships it is UNVERIFIED.
- Chrome/Edge: the Media Session API shows OS/hub media notifications; on desktop Chrome notifications appear in the media hub and Chrome only shows them for media of at least 5 seconds
  (https://web.dev/articles/media-session). The page does not say which Windows API Chrome uses, so that it appears in `GetSessions()` is UNVERIFIED.
- Games, Discord, Teams calls: no source; I would expect none of them to publish (UNVERIFIED), which would also keep calls out of the result.

**Simpler or more reliable than peak meters?** My judgement, not a sourced fact: SMTC gives `Playing/Paused` and track info per app with no threshold tuning and ignores calls, but only for apps that integrate (and browsers only with media-session metadata, 5 s minimum), needs Windows 10 1809+, a WinRT package (3.6 MB) and does not tell whether sound is actually audible (volume muted, 0 volume). Peak meters see every app but are a heuristic.

## Answer for Cuy
Yes: install `Microsoft.Windows.SDK.Contracts` (use 10.0.17763.x or newer) in the net48 WinForms project and read `GetSessions()` + `PlaybackStatus`; needs Windows 10 1809+.
Spotify (documented) and VLC (merge request, release unknown) report; browsers are likely via Media Session (UNVERIFIED); games/calls likely do not.
Threading: no documented STA/MTA issue found; avoid blocking `.Result` on the UI thread (UNVERIFIED practice).
SMTC is simpler for "music app is playing"; keep peak meters only as fallback for non-reporting apps.
