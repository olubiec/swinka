Question: On Windows 11, can a normal maximized window (Chrome, Edge, Explorer, Office) have a window rect equal to the monitor rect
and no WS_THICKFRAME? List known false positives of the "rect == monitor and no frame" check and how projects avoid them.

## Findings

Method note: pages were read through a summarising fetch tool, not opened by hand.

### Maximized windows normally do NOT match the monitor rect
- Raymond Chen (Microsoft blog): a maximised window's rect is larger than the screen because its invisible borders hang off the edges; top-left is around (-8,-8), bottom-right about 8 px past the edge.
  Windows 10/11 are not named in that post. https://devblogs.microsoft.com/oldnewthing/20150304-00/?p=44543 (Microsoft blog)
- Raymond Chen, 2012: since DWM (Vista) the overhang is hidden on screen, but `GetWindowRect` still returns the larger coordinates. https://devblogs.microsoft.com/oldnewthing/20120326-00/?p=8003 (Microsoft blog)
- Consequence: a plain `rect == monitor` test usually fails for a maximised thick-frame window. But a clip-and-compare test (Chromium's `IntersectRect` then `EqualRect`) passes it,
  which is why Chromium also rejects WS_THICKFRAME and WS_DLGFRAME. Source: [fullscreen_win.cc](https://chromium.googlesource.com/chromium/src/+/main/ui/base/fullscreen_win.cc).

### Known false positives / negatives of the geometry check
- Borderless or maximised-looking windows that exactly fill the monitor match the rect: reported in the Microsoft Q&A thread
  [Is there a way to detect when another app enters fullscreen?](https://learn.microsoft.com/en-us/answers/questions/1516325/is-there-a-way-to-detect-when-another-app-enters-f) (forum answer by RLWA32). Same thread: a `showCmd == SW_SHOWMAXIMIZED` test gives false negatives for fullscreen windows
  that are not maximised, and false positives for maximised windows with the taskbar visible.
- Desktop shell windows (Progman/WorkerW, `GetDesktopWindow`) cover the whole monitor and have no frame. Flow Launcher excludes them explicitly (see R13.2); Chromium does not special-case them. This is Cuy's existing bug.
- Taskbar view: Windows itself decides "fullscreen" from the client area covering the screen, ignoring the caption. An app can override with `ITaskbarList2::MarkFullscreenWindow` or the `NonRudeHWND` property.
  https://devblogs.microsoft.com/oldnewthing/20250522-00/?p=111211 (Microsoft blog)
- Chromium only tests the primary monitor (a limit, not a false positive).

### Windows 11 specifics
- No source found that tests Chrome, Edge, Explorer or Office on Windows 11. Whether Chromium-based apps with a custom frame keep WS_THICKFRAME when maximised: UNVERIFIED.

## Answer for Cuy
A normal maximised window overhangs the monitor by about 8 px and keeps WS_THICKFRAME, so "rect == monitor and no THICKFRAME/DLGFRAME" rarely fires on it; the real false positives are the desktop (Progman/WorkerW) and borderless windows that fill the screen.
Keep the style flags, add a desktop/shell exclusion like Flow Launcher's, and test Chrome/Edge/Explorer/Office maximised on a Windows 11 machine with a logging probe.
